## Root Cause Analysis — CMS `TextField` broken in `lis-request-app`

The screenshot shows the symptoms: inputs render with a blue filled background, no visible outlined border, and excessive height (~74px vs the expected ~40px). This is caused by **three compounding issues**, not one. Here they are in order of impact.

---

### Root Cause 1 — `lisBaseTheme` destroys the CMS `getMuiTextFieldTheme()` function (Primary)

This is the main cause. The chain is:

```
BasicThemeLight
  └── .components.MuiTextField.styleOverrides.root
        = getMuiTextFieldTheme()   ← a FUNCTION
              sets: backgroundColor, borderRadius, fieldset border colours
              based on ownerState.size (dynamic at render time)
```

`lis-hub-lib` builds `lisBaseThemeLight` like this:

ts

````ts
createTheme(BasicThemeLight, {
  components: {
    MuiTextField: { styleOverrides: { root: { /* plain object */ } } }
    // ...
  }
})
```

MUI's `createTheme` uses `deepmerge` internally. **`deepmerge` cannot merge a function with a plain object — it replaces the function.** After this call:
```
lisBaseThemeLight.components.MuiTextField.styleOverrides.root
  = LIS plain object   ← getMuiTextFieldTheme() is GONE
```

Result: any app that passes `lisBaseThemeLight` to `ThemeProvider` renders CMS `TextField` without the outlined border style, background fill, or border-radius — exactly what the screenshot shows.

**Why `lis-hub-lib` demo looks fine:** The demo wraps with `ThemeProvider theme={lisBaseThemeLight}` but doesn't compare carefully against the design spec. The broken rendering is there too — it just isn't caught.

**Why `lis-crs-common-app` looks fine:** It uses `BasicThemeLight`/`BasicThemeDark` **directly** in its `ThemeWrapper`, bypassing `lisBaseTheme` entirely. The CMS function is preserved.

---

### Root Cause 2 — `buildRegistrationTheme` padding stacking (Secondary, causes inflated height)

Even if Root Cause 1 were fixed, this would still produce wrong height. The sequence:
```
getMuiTextFieldTheme() sets:
  "& .MuiOutlinedInput-input": { padding: 0 }     ← from CMS
  wrapper padding: 12px 8px                        ← from CMS

buildRegistrationTheme() then adds:
  MuiInputBase.styleOverrides.input: {
    paddingTop: 6,
    paddingBottom: 6,                              ← injected AFTER, same specificity
  }
````

Emotion injects the later class after the CMS class. At equal specificity, last-wins. So the effective padding on the input is `6px top + 6px bottom` stacked on top of the wrapper's `12px` — producing ~74px total height instead of ~40px.

The `buildRegistrationTheme` override was intended to control font size but accidentally stomped the CMS padding rules.

---

### Root Cause 3 — `@emotion/react` singleton key missing `@` prefix (Amplifying)

In `craco.config.js`:

js

```js
// Wrong — webpack doesn't recognise these as module names
"emotion/react":  { singleton: true },
"emotion/styled": { singleton: true },

// Correct
"@emotion/react":  { singleton: true },
"@emotion/styled": { singleton: true },
```

Without the `@`, the singleton constraint has no effect. Each MFE bundles its own Emotion copy. This means:

- `@cmschassis/react-ui` uses **its own bundled Emotion instance** (from its `dependencies`)
- `lis-request-app` uses **its own separate Emotion instance**
- The `CacheProvider` from `lis-request-app`'s Emotion instance **does not intercept** style injection from `@cmschassis/react-ui`'s Emotion instance

So even if the scoped cache is set up correctly, CMS component styles bypass it and go to the default global Emotion stylesheet. This isn't what's causing the visual bug (the broken styling comes from the theme), but it means:

- Class name scoping is ineffective for CMS components
- CSS insertion order between the app and CMS components is unpredictable

### The Fix

**Fix 1 (Primary — fixes RC1):** In `ThemeAwareRoot.tsx`, use `BasicThemeLight`/`BasicThemeDark` directly as the theme base. Never pass through `lisBaseTheme`/`lisBaseThemeLight`. If you need LIS typography/spacing on top, nest a second `ThemeProvider`:

tsx

```tsx
import { BasicThemeLight, BasicThemeDark } from '@cmschassis/react-ui';
import { lisTypography, lisSpacing } from '@lis/lis-hub-lib'; // only if exported separately

// Option A — just use BasicTheme directly (simplest, correct)
const theme = cmsBase; // BasicThemeLight or BasicThemeDark

// Option B — if LIS spacing/typography overrides are truly needed
// Apply them via a separate plain createTheme that does NOT touch MuiTextField components
const theme = createTheme(cmsBase, {
  spacing: (factor) => `${factor * 1}px`,
  typography: lisTypography,
  // DO NOT include components.MuiTextField here
});
```

**Fix 2 (Secondary — fixes RC2):** In `buildRegistrationTheme`, remove the `MuiInputBase.styleOverrides.input` padding overrides. Font size for inputs should be set on `MuiInputBase.styleOverrides.root` as `fontSize` only, without touching padding:

ts

```ts
export function buildRegistrationTheme(base: Theme, fontSize: 14 | 18): Theme {
  return createTheme(base, {
    components: {
      MuiInputBase: {
        styleOverrides: {
          root: { fontSize },          // font size only
          // input: remove paddingTop/paddingBottom — these stomp CMS padding rules
        }
      },
      MuiInputLabel:   { styleOverrides: { root: { fontSize }, shrunk: { fontSize } } },
      MuiFormLabel:    { styleOverrides: { root: { fontSize } } },
      MuiMenuItem:     { styleOverrides: { root: { fontSize } } },
      MuiButton:       { styleOverrides: { root: { fontSize } } },
      MuiAutocomplete: { defaultProps: { size: 'small' } },
    },
  });
}
```

**Fix 3 (Amplifying — fixes RC3):** In all affected `craco.config.js` files:

js

```js
shared: {
  react:              { singleton: true, requiredVersion: "18.2.0" },
  "react-dom":        { singleton: true, requiredVersion: "18.2.0" },
  "@emotion/react":   { singleton: true },   // ← add @ prefix
  "@emotion/styled":  { singleton: true },   // ← add @ prefix
  "@emotion/cache":   { singleton: true },   // ← add this too
}
```

Apply Fix 1 and Fix 2 first — they'll resolve the visual bug immediately and are self-contained. Fix 3 is correct hygiene and should be done but it won't change the visible rendering on its own.

## The Actual Remaining Root Cause

The core problem is that **`@cmschassis/react-ui` bundles its own private copies of `@emotion/react`, `@emotion/styled`, and `@mui/material`** as hard `dependencies`, not `peerDependencies`. This is documented in the Theme Handling note:

> `@cmschassis/react-ui` bundles its own copies of `@emotion/react`, `@emotion/styled`, and `@mui/material` as regular `dependencies` (not `peerDependencies`).

This means there are **two completely separate Emotion instances** running simultaneously:

```
Instance A — your app's Emotion
  → controlled by your CacheProvider (key: "requestapp")
  → your ThemeProvider lives here
  → injects classes like css-requestapp-xxxxx

Instance B — @cmschassis/react-ui's bundled Emotion
  → knows nothing about your CacheProvider
  → knows nothing about your ThemeProvider
  → injects into the default cache (key: "css")
  → produces css-1u3bzj6, css-q8hpuo, etc. (what you're seeing)
```

Your `CacheProvider` and `ThemeProvider` are wrappers in Instance A's React context. When a CMS `TextField` renders, it calls `styled()` and `useTheme()` from **Instance B's** Emotion/MUI — which has no idea your providers exist. So:

- Theme styles: ignored (Instance B uses its own default theme)
- Cache scoping: bypassed (Instance B injects into `css-` prefix, not `requestapp-`)

**This is why fixing the theme base and removing the padding didn't help** — your `ThemeProvider` was never being read by CMS components in the first place.

## Why `lis-crs-common-app` works despite the same architecture

The doc says it uses `BasicThemeLight` directly and renders CMS TextField correctly. But the critical difference is likely that `lis-crs-common-app` has been running longer and the Emotion singleton from `@cmschassis/react-ui` happens to be the **same instance** already loaded by the hub. Because it's a Level-1 remote loaded directly into the Hub's JS context, and the Hub itself imports `@cmschassis/react-ui`, webpack's module deduplication may have resolved them to the same bundle. `lis-request-app` as a Level-2 remote has more isolation and gets a fresh copy.

## The Fix

The fix is to make `@cmschassis/react-ui`'s internal Emotion instance aware of your theme. Since you can't change how `@cmschassis/react-ui` is bundled, you need to intercept at the **MUI `StyledEngineProvider` level**, which controls where MUI/Emotion injects styles regardless of which Emotion instance is in use.

### Step 1 — Add `StyledEngineProvider` with `injectFirst`

This forces MUI style injection to happen before other styles, giving your theme rules the right insertion order:

tsx

```tsx
// ThemeAwareRoot.tsx
import { StyledEngineProvider, ThemeProvider } from '@mui/material/styles';
import { BasicThemeLight, BasicThemeDark } from '@cmschassis/react-ui';

export const ThemeAwareRoot: React.FC<{ children: React.ReactNode }> = ({ children }) => {
  const theme = /* your BasicThemeLight/Dark selection */;

  return (
    <StyledEngineProvider injectFirst>
      <ThemeProvider theme={theme}>
        {children}
      </ThemeProvider>
    </StyledEngineProvider>
  );
};
```

### Step 2 — Pass the Emotion cache container to the scoped `<style>` node

The root cause of CMS components bypassing your cache is that they use a different Emotion instance. The workaround is to **point the default Emotion cache insertion point** to the same container as your scoped cache, so both instances inject into the same DOM node in the right order.

In `view-handler.tsx`:

tsx

```tsx
import createCache from '@emotion/cache';
import { CacheProvider } from '@emotion/react';

function renderRegistrationComponent(container: HTMLElement, apiContext: LisApiContext) {
  // Create a <style> container INSIDE the plugin's DOM node
  const emotionRoot = document.createElement('style');
  container.appendChild(emotionRoot);

  // Scoped cache — your app's Emotion instance uses this
  const cache = createCache({
    key: 'requestapp',
    container: emotionRoot,
    speedy: false,         // false = styles visible in DOM for debugging
  });

  const root = createRoot(container);
  root.render(
    <StyledEngineProvider injectFirst>
      <CacheProvider value={cache}>
        <ThemeAwareRoot apiContext={apiContext}>
          <RegistrationPage />
        </ThemeAwareRoot>
      </CacheProvider>
    </StyledEngineProvider>
  );
}
```

The `container: emotionRoot` option tells Emotion where to inject `<style>` tags. This matches what `lis-crs-common-app` already does correctly (per the Theme Handling doc).

### Step 3 — Fix the `@` prefix in `craco.config.js`

This is still required. Even if two Emotion instances exist due to `@cmschassis/react-ui` bundling, fixing the singleton keys ensures your own app code and any other packages use the same instance:

js

```js
shared: {
  react:              { singleton: true, requiredVersion: "18.2.0" },
  "react-dom":        { singleton: true, requiredVersion: "18.2.0" },
  "@emotion/react":   { singleton: true },   // was "emotion/react" — missing @
```

## Yes — but it requires a one-line fix in `lis-hub-lib`

The reason `lisBaseThemeLight` breaks CMS `TextField` is entirely this in `lis-hub-lib/src/lib/components/Theme/theme/index.ts`:

ts

```ts
// Current — BROKEN
export const lisBaseThemeLight = createTheme(BasicThemeLight, {
  breakpoints,
  spacing: (factor) => `${factor * 1}px`,
  typography,
  components,   // ← this plain-object `components` block deepmerges over BasicThemeLight
                //   deepmerge replaces getMuiTextFieldTheme() function with a plain object
                //   CMS TextField loses its border, fill, and border-radius styling
});
```

The fix is to **remove `MuiTextField` (and any other CMS-styled components) from the `components` override block**. Only LIS-specific overrides that don't conflict with CMS components belong there.

ts

```ts
// Fixed — in lis-hub-lib
export const lisBaseThemeLight = createTheme(BasicThemeLight, {
  breakpoints,
  spacing: (factor) => `${factor * 1}px`,
  typography,
  components: {
    // Keep only overrides that DON'T touch MuiTextField, MuiOutlinedInput,
    // MuiInputBase, MuiSelect, MuiDatePicker — anything @cmschassis/react-ui owns
    MuiButton:     lisComponents.MuiButton,
    MuiIconButton: lisComponents.MuiIconButton,
    // ... whatever else is in the LIS components block that doesn't conflict
    // DO NOT include: MuiTextField, MuiOutlinedInput, MuiInputBase, MuiFormLabel
  },
});
```

Once that's published as a new `lis-hub-lib` version, `lisBaseThemeLight` becomes safe to use directly in all plugin apps. `lis-crs-common-app`, `lis-aps-app`, and `lis-request-app` can all switch to it.

## If you can't touch `lis-hub-lib` right now

You can reconstruct an equivalent safe theme locally in `lis-request-app` without waiting for a lib release. The key insight from the doc: `BasicThemeLight` already contains the CMS function. You need to add only `breakpoints`, `spacing`, and `typography` on top — **not** `components`:

ts

```ts
// theme-builder.ts in lis-request-app
import { BasicThemeLight, BasicThemeDark } from '@cmschassis/react-ui';
import { createTheme } from '@mui/material/styles';

// Import only the non-component parts from lis-hub-lib
// (or duplicate the values here if they aren't exported separately)
import { typography, breakpoints } from '@lis/lis-hub-lib';

export function buildRegistrationTheme(
  mode: 'light' | 'dark',
  fontSize: 14 | 18
): Theme {
  const cmsBase = mode === 'dark' ? BasicThemeDark : BasicThemeLight;

  // Step 1: Apply LIS spacing/typography/breakpoints — NO components block
  const withLisTokens = createTheme(cmsBase, {
    breakpoints,
    spacing: (factor: number) => `${factor * 1}px`,
    typography,
    // getMuiTextFieldTheme() on MuiTextField is still intact here
  });

  // Step 2: Apply font-size variant ONLY if needed, targeting only safe slots
  if (fontSize === 14) return withLisTokens;

  return createTheme(withLisTokens, {
    typography: {
      fontSize,   // MUI's global font size scalar — affects all typography variants
    },
    components: {
      // Safe to override — these are LIS-specific non-CMS components
      MuiButton:     { styleOverrides: { root: { fontSize } } },
      MuiMenuItem:   { styleOverrides: { root: { fontSize } } },
      // MuiInputBase: DO NOT touch — let CMS getMuiTextFieldTheme() own it
    },
  });
}
```
