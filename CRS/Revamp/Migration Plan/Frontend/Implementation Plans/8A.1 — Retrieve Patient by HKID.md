# Implementation Plan — 8A.1 Retrieve Patient by HKID

> [!info] Reference
> Workflow spec: [[Knowledge Base/01_Screens/Registration/Workflows/Retrieve Patient by HKID]]
> Migration plan task: [[Registration Migration Plan]] § Phase 8 — 8A.1

---

## Overview

This task wires the HKID field on the Registration Keys Panel to the patient retrieval workflow. When a valid HKID is entered, the system calls `lis-patient-svc` to retrieve matching local patient records. If PMI is configured, the user may also switch to PMI records. The selected episode populates the Patient Demographics panel and moves focus to Req No.

This plan covers:
- API integration for local patient lookup (`/api/lis/getPatientsByHkid`)
- API integration for PMI patient lookup by HKID (`/api/v2/getHkpmiPatientByHkid`)
- API integration for PMI patient lookup by encounter (`/api/v2/getHkpmiPatientbyEnc`)
- `SelectEpisodeDialog` component (local list and PMI list modes)
- Post-selection field population and state transitions
- PMI unavailability fallback (Message 4274 + Message 687)

### PMI Patient Lookup by HKID

| Property | Value |
|---|---|
| Service | `lis-patient-svc` |
| Endpoint | `POST /api/v2/getHkpmiPatientByHkid` |
| Generated function | `getHkpmiPatientByHkid(req: GetPatientByHkidRequest)` |
| Trigger | User clicks **PMI List** button |
| Returns | Single PMI patient record (not a list) |

> [!warning] Endpoint correction
> The previous plan referenced `getHkpmiPatientbyEnc` for the PMI List button. That endpoint requires `encounterNo + hospitalCode`, not `hkid`. **PMI lookup by HKID must use `getHkpmiPatientByHkid`.**
> `getHkpmiPatientbyEnc` is used when re-loading PMI data for a known encounter (e.g. Close Indicator flow where an encounter is already selected).

**Request — `GetPatientByHkidRequest`** (`@/generated/model/getPatientByHkidRequest`):

```typescript
interface GetPatientByHkidRequest {
  hkid:                string;        // required
  serviceParameter?:   ServiceParameterVo;
  hospitalCode?:       string;
  retrieveLinkedHkid?: boolean;
  retrieveEhr?:        boolean;
}
```

**Response — `ResultDataResponsePasPatientResponseVo`** (`@/generated/model/resultDataResponsePasPatientResponseVo`):

```typescript
interface ResultDataResponsePasPatientResponseVo {
  code?:      number;
  message?:   string;
  data?:      PasPatientResponseVo;   // single record, not array
  timestamp?: number;
}

interface PasPatientResponseVo {
  pasPatientInfoVo?:   PasPatientInfoVo;    // { pasPatientKey? }
  patientVo?:          PatientVo;           // same PatientVo as local lookup
  linkedPatientVo?:    LinkedPatientVo;
  ehrPatientDetailVo?: EhrPatientDetailVo;
}
```

> [!note] PMI response vs local response
> Local lookup returns `PatientVo[]` (multiple episodes). PMI by HKID returns a single `PasPatientResponseVo` wrapping one `PatientVo` plus EHR and linked patient data. The `SelectEpisodeDialog` PMI mode will show the single PMI record's encounters by expanding `patientVo.encounterInfoVo`.

## State Design

Extend `RegistrationScreenState` (defined in 2.0.C) with patient retrieval state.
Use generated types directly — no hand-written `PatientEpisodeVo`:

```typescript
import type { PatientVo } from '@/generated/model/patientVo';
import type { PasPatientResponseVo } from '@/generated/model/pasPatientResponseVo';

interface PatientRetrievalState {
  status:              'idle' | 'loading' | 'episode-selection' | 'loaded' | 'error';
  hkid:                string | null;
  localPatients:       PatientVo[];             // from getPatientsByHkid
  pmiPatient:          PasPatientResponseVo | null; // from getHkpmiPatientByHkid
  pmiLoading:          boolean;
  pmiAvailable:        boolean;                 // from Hub BFF config
  pmiUnavailableError: boolean;
  selectedPatient:     PatientVo | null;
  dialogMode:          'local' | 'pmi';
}
```

`screenMode` transitions:
- `idle` → lookup starts → `loading`
- `loading` → records returned → `episode-selection` (dialog opens)
- `episode-selection` → row selected → `loaded` → `screenMode: 'patient-ready'`
- `episode-selection` → dialog closed without selection → `idle`

## Hook: `useRetrievePatientByHkid`

```typescript
import type { PatientVo } from '@/generated/model/patientVo';

function useRetrievePatientByHkid(options: {
  pmiAvailable:     boolean;
  onPatientLoaded:  (patient: PatientVo) => void;
  onCreateNewPatient:(hkid: string) => void;   // triggers 8A.3
  onShowMessage:    (code: number) => void;
}): {
  state:                       PatientRetrievalState;
  handleHkidConfirmed:         (hkid: string) => void;
  handlePmiListClick:          () => void;
  handlePatientSelected:       (patient: PatientVo) => void;
  handleDialogClose:           () => void;
  handleGenerateComputerEncounter: () => void;
}
```

### `handleHkidConfirmed(hkid)`

Fired when `HkidInput` receives Enter key or blur with a valid HKID (check digit passes). See **HkidInput Trigger** section below.

1. Set `status: 'loading'`, store `hkid`.
2. Call `getPatientsByHkid({ hkid })`.
3. On success: set `localPatients: data ?? []`, `status: 'episode-selection'`, `dialogMode: 'local'`.
4. On error: set `status: 'error'`, display on log monitor.

### `handlePmiListClick()`

1. Set `pmiLoading: true`.
2. Call `getHkpmiPatientByHkid({ hkid })`.
3. On success: set `pmiPatient: data`, `pmiLoading: false`, `dialogMode: 'pmi'`.
4. On failure: set `pmiLoading: false`, `pmiUnavailableError: true`, show Message 4274, then Message 687.

### `handleDialogClose()` (from local mode Close ✕)

Implements **Close Indicator Behaviour** (Scenario 3):

1. If `pmiAvailable`:
   a. Call `getHkpmiPatientByHkid({ hkid })`.
   b. If PMI record found (`data` non-null) → switch `dialogMode: 'pmi'`, set `pmiPatient`.
   c. If PMI record empty → show Message 687 ("Create new Encounter case?") via `MessageBoxApi`.
      - Yes → `onCreateNewPatient(hkid)`.
      - No → close dialog, `status: 'idle'`.
   d. If PMI call fails → show Message 4274 via `MessageBoxApi`, chain Message 687 in its `Ok` callback. Same Yes/No branching.
2. If `!pmiAvailable`: close dialog, `status: 'idle'`.

### `handlePatientSelected(patient)`

1. Set `selectedPatient`, `status: 'loaded'`.
2. Call `onPatientLoaded(patient)`.
3. Close dialog.

### `handleGenerateComputerEncounter()`

Generates a computer encounter by calling `sysgenEncounterNo(labCode, stationId)` from `lis-hub-lib/ConversionUtility`. This is **in-scope for this task** — it runs entirely on the client and requires no API call.

```typescript
import { sysgenEncounterNo } from '@lis/lis-hub-lib';

function handleGenerateComputerEncounter() {
  const encounterNo = sysgenEncounterNo(labCode, stationId);
  // Set encounterNo in screen state, then call onCreateNewPatient(hkid)
  // This follows the same path as 8A.3 (new patient flow)
  onCreateNewPatient(hkid);
}
```

`labCode` and `stationId` come from the lab session context (Hub BFF dictionary / lab options). The generated encounter no is prefixed with `%` which identifies it as computer-generated.

> [!note] Legacy reference
> In `RegistrationUIComponents.as`, `processCreateNewEncounterEpisode()` calls `ConversionUtility.sysgenEncounterNo()` when the HKID path is used, then passes the generated encounter no to `popUpCreateNewEpisodeDialogue`. The format is identical. `triggerActionForNewPatientForAutoFill()` also calls this function directly without a pop-up when auto-fill is active.

## HkidInput Trigger

`HkidInput` fires `onConfirm` on **Enter key or blur** — both events trigger the lookup, provided the check digit is valid.

- This matches the legacy `hkidModifiedFunction` in `RegistrationUIComponents.as`, which is bound to `hkidPm.modifiedFunction` — the legacy `LisHkidTextInputPm.modifiedFunction` fires on both ENTER and field blur.
- The check digit validation runs first (inside `HkidInput`). An invalid HKID shows Message 4273 and clears the field; it does not reach `handleHkidConfirmed`.
- If the HKID field is blank on blur, no action is taken (the hook is not called).

> [!note] Legacy reference
> `hkidModifiedFunction` (line ~2890) in `RegistrationUIComponents.as`:
> ```actionscript
> if (hkid.length > 0) {
>   if (hkidPm.validateCheckDigit(hkid)) {
>     gatherPatientInformationByHkid(hkid);  // → retrievePatientList → open dialog
>   } else {
>     hkidPm.promptErrorMessageWithParams("", "0004273", ...);  // invalid check digit
>   }
> } else {
>   keyComponentPm.dispatchEvent(MODIFIED_SUCCESS);  // blank = no-op
> }
> ```

```typescript
MessageBoxApi.open({
  tag: 'PTLKUP',
  code: 4274,
  params: [],
  actionsCallback: {
    Ok() {
      MessageBoxApi.open({
        tag: 'PTLKUP',
        code: 687,
        params: [],
        actionsCallback: {
          Yes() { onCreateNewPatient(hkid); },
        },
      });
    },
  },
});
```

> [!important] Do NOT use MUI `Dialog` or `window.confirm` for these messages
> Both are system messages with dictionary codes — they must go through `MessageBoxApi` so they are consistently logged and auditable.

## Category Handling

`EncounterDetailVo.category` is typed as `number` in the generated model. This number represents the **alpha2 value** of a `LisKeyword` in the `PATIENT_CATEGORY` keyword group — it is **not** a display string.

- The legacy `categoryPm` (a `LisKeywordComboBoxPm`) is loaded via `setSelectedItemByAlpha2(value.toString())`.
- In the revamp, `category` must be passed to the `KeywordDropdown` for the `PATIENT_CATEGORY` keyword group using its `alpha2` value as the selection key.
- The `KeywordVo` data source for patient category provides the mapping: `alpha2 (number) → display label`.
- A `null` category in the response maps to "Unknown" (`PATIENT_CATEGORY_UNKNOWN_TEXT` in the legacy constant).

**Category editable exception (from legacy `loadDataToComponents` / `enableComponents`):**

In `STATE_READY` (after Req No is entered), `categoryPm.editable = true` always. The demographic editability depends on `isNewPatient` and `isExistingPatientDemoDisabled`. However, the **category source logic** at `PATIENT_LOADED` time is:

| Condition | Category source |
|---|---|
| General lab (`isPatientCategoryDerivedFromPatientLocation = true`) | Taken from Location's patient category (`patientLocationPm.locationPatientCategory`) — NOT from `encounterInfoVo.encounterDetail.category` |
| Special lab (`isDefaultPatCategoryFromPatient = true`) OR new PMI patient | Taken from `encounterInfoVo.encounterDetail.category` (the number from `PatientVo`) |
| Null / Unknown category | Set to "Unknown" value |

> [!warning] Lab-dependent category logic
> Whether `category` from `PatientVo` is actually used depends on the lab dictionary flag `isPatientCategoryDerivedFromPatientLocation`. For most general labs, the category shown comes from the resolved patient location, not the `PatientVo` field. Implement the flag-based switch in the `PATIENT_LOADED` reducer. Flag availability: from `dictionaryParam` (Hub BFF dictionary options).

## Post-Selection: Field Population

`onPatientLoaded` maps `PatientVo` nested fields to screen state:

```typescript
import type { PatientVo } from '@/generated/model/patientVo';

function applyPatientToScreen(patient: PatientVo, dispatch: Dispatch) {
  const id      = patient.patientInfoVo?.patientId;
  const detail  = patient.patientInfoVo?.patientDetail;
  const encId   = patient.encounterInfoVo?.encounterId;
  const encDet  = patient.encounterInfoVo?.encounterDetail;

  dispatch({
    type: 'PATIENT_LOADED',
    payload: {
      hkid:           id?.hkid,
      encounterNo:    encId?.encounterNo,
      encounterHosp:  encId?.hospital,      // needed for gatherPatientInformation call on row select
      name:           detail?.name,
      sex:            detail?.sex,
      dob:            detail?.dob,
      age:            detail?.age,
      ageUnit:        detail?.ageUnit,
      dod:            detail?.dod,          // for death indicator display
      cccCode:        detail?.cccCode,      // for Chinese name display
      locHospital:    encId?.hospital,
      locWard:        encDet?.location?.ward,
      locSpecialty:   encDet?.location?.specialty,
      wardClass:      encDet?.wardClass,
      bed:            encDet?.bed,
      admitted:       encDet?.admissionDate,
      category:       encDet?.category,     // numeric alpha2 — see Category Handling
      mrn:            encDet?.mrn,
      race:           detail?.race,
      confidential:   detail?.confidential,
      address:        detail?.address,
      payCode:        encDet?.type,         // "type" field maps to Pay Code display
      attendDoctor:   encDet?.attendDoctor?.ward, // doctor code for default request doctor
    },
  });
}
```

> [!note] attendDoctor → Request Doctor default
> `encounterInfoVo.encounterDetail.attendDoctor.ward` contains the doctor code that defaults to the Request Doctor field, conditional on `isCopyPatAttnDoctorToReqDocProhibited = false` and the current request doctor being blank. This is applied in `loadDataToComponents` (legacy), which runs after `loadPatientReadyDataToComponents`. In the revamp, this mapping should be part of the `PATIENT_LOADED` reducer / post-selection logic in step 8A.1.8.

The `PATIENT_LOADED` reducer also:
- Sets `screenMode: 'patient-ready'` — all patient demographic fields become dimmed (`disabled={true}`)
- **Category exception:** remains editable when `isNewPatient && demographicsEditingAllowed && category === ''`
- Populates `encounterNo` in the Keys Panel

**Focus after load:** move focus to `Req No.` field via `useEffect` watching `screenMode === 'patient-ready'`.
