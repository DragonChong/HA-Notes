# Implementation Plan — 8A.2 Retrieve Patient by Encounter Number

> [!info] Reference
> Workflow spec: [[Knowledge Base/01_Screens/Registration/Workflows/Retrieve Patient by Encounter Number]]
> Migration plan task: [[Registration Migration Plan]] § Phase 8 — 8A.2
> Related user stories: CRST-96, CRST-97

---

## Overview

This task wires the **Enc No.** field on the Registration Keys Panel to the patient retrieval workflow. When an encounter number is entered, the system immediately prompts the user to select a hospital via `HospitalSelectionDialog`, then searches local patient records by hospital and encounter number. If no local record is found and PMI is configured, the system queries the PMI service. The retrieved patient episode populates the Patient Demographics panel and moves focus to Req No.

> [!note] Workflow change from legacy
> The legacy system validated the encounter number's check digit first and only opened hospital selection on check digit failure (Error 3214). In the revamp, **hospital selection is always prompted first** on encounter number entry, before any lookup is attempted. This removes the check digit path as a conditional branch and simplifies the flow into a single linear sequence: enter encounter → select hospital → lookup local → lookup PMI if needed.

This plan covers:
- `HospitalSelectionDialog` component
- API integration for local patient lookup by encounter (`/api/lis/getPatientByEncounter`)
- API integration for PMI patient lookup by encounter (`/api/v2/getHkpmiPatientbyEnc`)
- `useRetrievePatientByEncounter` hook
- Post-selection field population and state transitions
- PMI unavailability fallback (Message 4274 + Message 687)

## State Design

Extend `RegistrationScreenState` with encounter-specific retrieval state. Reuse `PatientVo` and `PasPatientResponseVo` from 8A.1:

```typescript
import type { PatientVo } from '@/generated/model/patientVo';
import type { PasPatientResponseVo } from '@/generated/model/pasPatientResponseVo';

interface EncounterRetrievalState {
  status:              'idle' | 'hospital-selection' | 'loading' | 'loaded' | 'error';
  encounterNo:         string | null;
  selectedHospital:    string | null;           // hospitalCode from HospitalSelectionDialog
  localPatient:        PatientVo | null;         // from getPatientByEncounter
  pmiPatient:          PasPatientResponseVo | null; // from getHkpmiPatientbyEnc
  pmiLoading:          boolean;
  pmiAvailable:        boolean;                 // from Hub BFF config
  pmiUnavailableError: boolean;
}
```

`screenMode` transitions:
- `idle` → encounter entered → `hospital-selection` (dialog opens)
- `hospital-selection` → hospital selected → `loading` (local lookup fires)
- `hospital-selection` → dialog cancelled → `idle` (encounter number cleared)
- `loading` → local record returned → `loaded` → `screenMode: 'patient-ready'`
- `loading` → no local record + PMI enabled → `pmiLoading: true` → PMI lookup
- PMI result → `loaded` → `screenMode: 'patient-ready'`
- PMI no record / error → `idle` (after 4274 + 687 prompt)

## Hook: `useRetrievePatientByEncounter`

```typescript
import type { PatientVo } from '@/generated/model/patientVo';

function useRetrievePatientByEncounter(options: {
  pmiAvailable:     boolean;
  hospitals:        HospitalVo[];
  onPatientLoaded:  (patient: PatientVo, isPmi: boolean) => void;
  onCreateNewEpisode:(encounterNo: string) => void;    // triggers new episode flow
  onShowMessage:    (code: number) => void;
}): {
  state:                    EncounterRetrievalState;
  handleEncounterEntered:   (encounterNo: string) => void;
  handleHospitalSelected:   (hospitalCode: string) => void;
  handleHospitalDialogClose:() => void;
}
```

### `handleEncounterEntered(encounterNo)`

Fired when `EncounterInput` receives Enter key or blur with a non-empty value.

1. Store `encounterNo` in state.
2. Set `status: 'hospital-selection'` — this opens `HospitalSelectionDialog`.

> [!note] No check digit validation at this stage
> Unlike the legacy flow, there is no check digit validation before showing the hospital selection dialog. The encounter number is accepted as entered and the hospital is always selected explicitly by the user.

### `handleHospitalDialogClose()`

Fired when the user cancels `HospitalSelectionDialog`.

1. Set `status: 'idle'`, clear `encounterNo` and `selectedHospital`.
2. Clear the Enc No. field in screen state.

### `handleHospitalSelected(hospitalCode)`

Fired when the user selects a hospital in `HospitalSelectionDialog`.

1. Set `selectedHospital: hospitalCode`, `status: 'loading'`.
2. Close `HospitalSelectionDialog`.
3. Call `getPatientByEncounter({ encounterNo, hospitalCode })`.
4. On success with data: call `onPatientLoaded(data, false)` → dispatches `PATIENT_LOADED`.
5. On success with no data (empty / null):
   - If `pmiAvailable`: proceed to PMI lookup (see below).
   - If `!pmiAvailable`: show Message **687** ("Create new Encounter case?")
     - Yes → `onCreateNewEpisode(encounterNo)`
     - No → `status: 'idle'`, clear encounter number
6. On API error: set `status: 'error'`, display on log monitor.

**PMI lookup path** (when local lookup returns nothing and PMI is enabled):

```typescript
async function fetchPmi(encounterNo: string, hospitalCode: string) {
  set({ pmiLoading: true });
  try {
    const res = await getHkpmiPatientbyEnc({ encounterNo, hospitalCode });
    if (res.data?.patientVo) {
      onPatientLoaded(res.data.patientVo, true);   // isPmi = true
    } else {
      // PMI record not found
      showMessage4274ThenMessage687();
    }
  } catch {
    // PMI service error
    showMessage4274ThenMessage687();
  } finally {
    set({ pmiLoading: false });
  }
}
```

### Message 687 — Create New Encounter Case?

```typescript
MessageBoxApi.open({
  tag: 'PTLKUP',
  code: 687,
  params: [],
  actionsCallback: {
    Yes() {
      onCreateNewEpisode(encounterNo);
    },
  },
```

When chained after Message 4274:

```typescript
MessageBoxApi.open({
  tag: 'PTLKUP',
  code: 4274,
  params: [],
  actionsCallback: {
    Ok() {
      MessageBoxApi.open({
        tag: 'PTLKUP',
        code: 687,
        params: [],
        actionsCallback: {
          Yes() { onCreateNewEpisode(encounterNo); },
        },
      });
    },
  },
});
```

> [!important] Do NOT use MUI `Dialog` or `window.confirm` for these messages
> Both are system messages with dictionary codes — they must go through `MessageBoxApi` so they are consistently logged and auditable. Same pattern as 8A.1.

## PMI Patient Indicator

When `onPatientLoaded` is called with `isPmi = true`, the `PATIENT_LOADED` action payload must include a `isPmiPatient: true` flag. The Registration Keys Panel renders a lock indicator (🔒) next to the HKID field whenever `isPmiPatient` is `true` in screen state.

```typescript
// In PATIENT_LOADED reducer
case 'PATIENT_LOADED':
  return {
    ...state,
    ...applyPatientFields(action.payload),
    isPmiPatient: action.payload.isPmi ?? false,
    screenMode: 'patient-ready',
  };
```
